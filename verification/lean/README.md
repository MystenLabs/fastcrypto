# Lean

Proofs that fastcrypto-threshold's AVSS (`threshold_schnorr::avss`) meets the contracts of
[fastcrypto-specs](https://github.com/jonas-lj/fastcrypto-specs), against a Lean translation of the
Rust code made by [Charon and Aeneas](https://github.com/AeneasVerif/aeneas). The Rust sources carry
no annotations. `avss.rs` is written in a style Aeneas can translate (loops instead of iterator
chains), and under `cfg(aeneas)`, which Charon sets, it compiles its `tracing` logging out.

| Path | Contents |
|---|---|
| `Avss/` | The translation of `avss.rs`, generated by `extract.sh`. Code outside `avss.rs` is opaque: Lean sees only the signatures of what `avss.rs` calls in other modules and crates, and of `Poly::eval`. |
| `AvssProofs/` | The proofs. `Link.lean` proves the contracts of fastcrypto-specs from the theorems in the other files. `Result.lean` has the `ok_inv` tactic most proofs use. |
| `extract.sh` | Regenerates `Avss/`. |
| `fix_aeneas_output.py` | Patches Aeneas output that Lean rejects. Called by `extract.sh`. |

To check the proofs, install Lean with `elan` and run `lake build` here. To regenerate `Avss/`
after changing `avss.rs`, get `charon` and `aeneas` from the Aeneas release named in `extract.sh`
and run `CHARON=... AENEAS=... ./extract.sh`.

## What is proved

`AvssProofs.Link.contracts` proves `FastcryptoSpecs.Avss.Contracts` (`Avss/Steps.lean` in
fastcrypto-specs, at the commit in `lakefile.lean`) for `Link.api`, the spec's `Api` built from the
generated functions:

* The parties are the ids that `nodes.weight_of` accepts, and `weight(j)` is what it returns. `t`
  and `f` are those of `params`.
* Party `j` runs the receiver `recv(j)`, whose id is `j`. All receivers have the same `nodes`,
  `params`, `sid` and `commitment`. `recv(j)` passes the randomness `rng(j)` to `process_message`.
* A Rust `Err`, a panic, and a call that does not return all become the spec's `none` (or
  `invalid` for `process_message`).

Each contract follows from a theorem about the generated functions:

| Rust function | Contract | Theorem |
|---|---|---|
| `Receiver::verify_complaint_response` | `Ok(v)` ⇒ `v.responder_id = j`. | `verify_binds` |
| `Receiver::recover` | `Ok(o)` ⇒ `o.my_shares.verify(m, share_ids_of(i), i)` is `Ok`. | `recover_sound` |
| `Receiver::process_message` | `Ok(Valid(o))` ⇒ `o.my_shares.verify(m, share_ids_of(i), i)` is `Ok`. | `process_valid` |
| `Receiver::process_message` | `Rᵢ.process_message(m)` is `Err` ⇔ `Rⱼ.process_message(m)` is `Err`. | `process_invalid_iff` |
| `Receiver::handle_complaint` | `Rᵢ.process_message(m) = Ok(Complaint(c))` and `Rⱼ.process_message(m) = Ok(Valid(o))` ⇒ `Rⱼ.handle_complaint(m, i, c, o)` is `Ok`. | `handle_accepts` |
| `Receiver::verify_complaint_response` | `Rⱼ.process_message(m) = Ok(Valid(o))` and `Rⱼ.handle_complaint(m, i, c, o) = Ok(r)` ⇒ `Rᵢ.verify_complaint_response(m, j, r)` is `Ok`. | `response_verifies` |
| `Receiver::recover` | `Rᵢ.process_message(m)` is not `Err`, and `vs` are responses returned by `Rᵢ.verify_complaint_response` for `m`, from distinct parties of total weight `≥ t` ⇒ `Rᵢ.recover(m, vs)` is `Ok`. | `recover_complete` |
| `SharesForNode::verify` | `Rᵢ.process_message(m)` is not `Err` ⇒ there is a `p` with `p.degree() < t` such that `sh.verify(m, share_ids_of(j), j)` is `Ok` ⇒ `sh.shares = [p.eval(k) for k in share_ids_of(j)]`. | `feldman_binding` |

`create_valid` and `create_secret`, which are about `Dealer::create_message`, are not proved: they
are hypotheses of `contracts`. Their statements are about the distribution of `create_message`'s
messages, and the generated code does not include the dealer.

`Rotation.lean` proves the two contracts of the spec's `RotationContracts` for key rotation:

| Rust function | Contract | Theorem |
|---|---|---|
| `Receiver::process_message` | For receivers created with `commitment = Some(G::generator() * s)`: `Rᵢ.process_message(m)` is not `Err` ⇒ every `p` with `p.degree() < t` such that `sh.verify(m, share_ids_of(j), j)` is `Ok` ⇒ `sh.shares = [p.eval(k) for k in share_ids_of(j)]` has `p.c0() = s`. | `process_matches_commitment` |
| `DkOutput::complete_key_rotation` | `complete_key_rotation(t, i, outputs) = Ok(dk)` and each output holds the shares `[(k, v_o(k)) for k in share_ids_of(i)]` ⇒ `dk.my_shares = [(k, w(k)) for k in share_ids_of(i)]` with `recover_c0(t, [(u, v_o(k)) for (u, o) in outputs]) = Ok(w(k))`. | `rotation_interpolates` |

On the way, `VerifyComplete.lean` proves that `SharesForNode::verify` accepts shares whose indices
are the expected ids and that each pass `verify_share`, and `KeyRotation.lean` proves what
`complete_key_rotation` returns: each share is the sum of the outputs' shares at its index, times
their Lagrange coefficients.

From `contracts`, `Link.lean` states these theorems of fastcrypto-specs for the generated code,
under `Link.Assumptions` (the hypotheses below, together):

| Theorem | Statement |
|---|---|
| `every_honest_party_gets_valid_shares` | Liveness: for a certified message, every honest party eventually holds shares that pass `SharesForNode::verify`, directly or through complaints and `recover`. Under the execution model of `Avss/Protocol.lean`. |
| `honest_outputs_agree` | All outputs honest parties hold for a certified message fit one polynomial of degree `< t`. |
| `honest_dealer_no_complaints` | If every receiver finds the message valid, every honest party gets valid shares from `process_message` and never complains. |

The other AVSS theorems of fastcrypto-specs either assume nothing about the code
(`honest_dealer_certifiable`, `corrupt_can_block_certificate`, `accepted_same_cert`, and so on), or
also need the contracts of `polynomial.rs` (`Shamir.Contracts`) and of `complete_dkg`
(`DkgContracts`), which are not proved here: `honest_shares_recover_same_secret` and the DKG
theorems.

## What is assumed

* The translation: Charon, Aeneas and `fix_aeneas_output.py`. The script changes the translation:
  * serde's traits are mutually recursive, which Lean rejects. Their structures are emptied, and
    the derived `Serialize` and `Deserialize` code of the AVSS types becomes axioms. No proof uses
    serialization.
  * `core::num::nonzero::ZeroablePrimitive` gets two fields with the same name. One is renamed.
  * An instance that refers to itself (the `BCSSerialized` impl of `SharesForNode`), and any
    function whose body Aeneas could not translate (`check_recovery_proof`, because of its
    closure), become axioms.
  * A Rust parameter named `nodes` (of `complete_key_rotation`) shadows the `nodes` module, so
    the generated code refers to that module's functions from the root namespace.
  * Two functions that Aeneas' library does not model are defined: `Result::is_err` returns `true`
    exactly for `Err`, and `IntoIterator::into_iter` for `&Vec` returns an iterator over the
    vector's elements.
* The opaque functions are arbitrary: nothing is assumed about what they return, except by the
  hypotheses below.
* Hypotheses of `contracts`, defined in `AvssProofs/`:
  * `CloneIsId`, `PolyCloneIsId`: `SharesForNode::clone` and `Poly::clone` return an equal value.
    Their code calls the `Clone` impls of opaque types.
  * `PolyEqRefl`: `Poly::eq` of a polynomial with itself is `true`.
  * `RecoveryComplete`, the completeness of the recovery proof: for receivers configured alike, a
    complaint that `Rᵢ.create_complaint` makes about a message whose shares `Rᵢ.verify_message`
    rejected is accepted by `Rⱼ.check_recovery_proof`.
  * `InterpolationComplete`, the completeness of share recovery, which depends on the `Nodes`
    functions and on polynomial interpolation: for a message that passes `Rᵢ.check_message`, the
    shares of responses that `Rᵢ.verify_complaint_response` returned for distinct responders of
    total weight `≥ t` make `SharesForNode::recover` return shares that verify for `Rᵢ`.
  * `CommitmentBinding`, the binding of Feldman commitments over secp256k1, which depends on the
    group and on `Poly::verify_share` and `Poly::eval`: a commitment of degree `d` commits to a
    polynomial `p` over the scalars of degree at most `d`, and a share passes `verify_share` only
    if its value is `p.eval` at its index.
  * Every party has share ids (`share_ids_of(j)` is `Ok`), and the weights of any set of parties
    add up to at most `u16::MAX`.
  * `process_message` returns, without a panic, for every party and message.
  * `create_valid` and `create_secret`, see above.
* Hypotheses of `process_matches_commitment`, defined in `AvssProofs/Rotation.lean`:
  * `CommitmentOpening`, which implies `CommitmentBinding`: a commitment `c` of degree `d` commits
    to a polynomial `p` of degree at most `d` whose `eval` returns, a share passes `verify_share`
    exactly when its value is `p.eval` at its index, and `c.c0() = G::generator() * p.c0()`.
  * `gen`, the map `s ↦ G::generator() * s` from the spec's field to secp256k1 points, is
    injective.
  * `PointEqSound`: `PartialEq` for secp256k1 points returns `true` only for equal points.
  * `SharesCoverT`: the parties' share ids include `t` distinct indices.
  * `Shamir.Contracts`, the spec's contracts for `polynomial.rs`, for the scalar-polynomial
    functions of the link. Only `recover_c0` is used: polynomials of degree `< t` that agree at
    `t` indices have the same `c0()`.
  * `NonZeroModel`, as for `contracts`.
* Hypotheses of `rotation_interpolates`:
  * `ScalarHom`: the map from secp256k1 scalars to the spec's field takes the scalar `zero`, `+=`
    and `*` that `complete_key_rotation` uses to the field's.
  * `LagrangeRecover`: `Poly::recover_c0` is `Σⱼ yⱼ·λⱼ·c` for the coefficients `(c, λ)` that
    `get_lagrange_coefficients_for_c0` returns for the same indices, as `recover_c0` computes it.
  * `NonZeroModel`, as for `contracts`.
  * `complete_dkg`, which uses a `HashMap`, is not translated and stays abstract.
* What the spec needs that the generated code does not give, in `Link.Scalars`:
  * The scalar field `F` and a map from secp256k1 scalars to it. Lean sees the scalars as an opaque
    type.
  * `ofIndex`, which makes a share index into a `NonZeroU16`, with `NonZeroModel`: `get()` of a
    `NonZeroU16` returns a positive value that determines it, and `get()` of `ofIndex(k)` is `k`.
    Lean sees `NonZero` as an opaque type.
  * The scalar-polynomial functions of the spec that AVSS does not call (`rand_fixed_c0`, `add`,
    `mul`, `recover_c0`). `eval`, `degree_bound` and `c0` are the generated `Poly::eval`,
    `Poly::degree` and `Poly::c0`.
* The dealers stay abstract (`Link.Dealers`): their type, `create_message`'s distribution and
  their `secret`.
